# qqq_monitor 首版实施与验收计划

本计划把 [技术方案](TECHNICAL_PLAN.md) 与 [架构设计](ARCHITECTURE.md) 转为可执行开发阶段。按技术验证、基础模块、真实采集、完整 GUI、发布检查推进；每个阶段以可演示结果和运行时证据作为完成条件。

当前已建立 Workspace、监控引擎、四类核心采集和六个 GUI 页面。已经通过 8 项运行时测试、fmt、Clippy、Release 构建，以及 Windows 11 非管理员账户的真实采集和页面截图检查；本机验证细节见 [验证记录](VALIDATION.md)。下面的条目仍是完整首版验收清单，未验证项不因模块已实现而自动通过。

| 阶段 | 当前状态 | 主要剩余项 |
| --- | --- | --- |
| 技术验证 | DX12、依赖配套、中文字体和原生采集已通过本机检查 | 多 DPI、发行依赖、可选 GPU |
| 模块与引擎 | 已实现并有运行时验证 | 强制丢批、连续保存、局部失败与设备清理的更多场景 |
| 核心采集 | 四类真实采集已接通 | 热插拔、睡眠恢复、其他机器与驱动 |
| GUI | 六页面、图表、设备选择、设置已实现 | 人工交互、键盘、多屏 DPI、最小窗口 |
| 稳定性与发行 | 待完整验收 | 5 分钟预算、8 小时运行、日志总量上限、干净环境 |

首版核心验收只包含 CPU、内存、磁盘、网络与 GUI；GPU 单独评估，不能成为核心发布的隐含阻塞条件。

## 阶段零 技术验证

在现有项目中验证最小链路，记录结果后沿目标结构继续原地完善。验证用到的临时示例应明确标识，确认结果已保存且不再需要后才能移除。

| 验证项 | 要回答的问题 | 通过条件 |
| --- | --- | --- |
| GUI 与渲染 | 候选 eframe、egui_plot 是否配套；DX12 能否启动 | Windows 11 普通账户运行原生窗口和一条曲线，重复依赖检查可解释 |
| 中文与 DPI | 字体覆盖、体积、后备字体和多屏缩放是否可用 | 中文标签和真实设备名称可读，100%、150%、200% 下不截断关键内容 |
| CPU 与网络 | sysinfo CPU 最低间隔、IP Helper 计数和预热是否满足 0.5 秒设置 | 至少两轮采样后得到有效值，累计字节差和实际间隔一致 |
| 磁盘 PDH | 语言中立计数器、物理盘实例与有效读数 | 中文 Windows 上普通权限可读取读写速率；失败状态可识别 |
| 设备映射 | 卷、盘符、物理磁盘、网卡身份如何关联 | 盘符不作为物理磁盘主键，同一网卡重命名不会重复统计 |
| 可选 GPU | adapter LUID、引擎、显存计数是否可靠 | 确认数据范围与聚合口径；结果决定是否纳入首版 |
| 发行依赖 | 干净机器是否缺 MSVC/DXC 等组件 | 明确便携包所需文件，不能只在开发机运行 |

输出简短验证记录，写明 OS、GPU、驱动、crate 组合、运行权限、观察结果和局限。记录可以在实施过程中加入同一 `docs` 目录；通过结果更新现有设计文档，不另外维护平行方案。

## 阶段一 建立模块和引擎骨架

将根包改为 Workspace 启动入口，建立四个库 crate，集中依赖和 lint。定义设备、指标、单位、状态、CollectorFactory、MonitorClient 和 MonitorRuntime；用假采集器驱动引擎。

实现有界通道、最新 Arc 视图槽、差分与预热、历史时间与容量限制、命令确认和独立取消信号。引擎不能依赖平台或 GUI crate，领域层不能引入系统调用。

完成条件：

- Workspace 可以编译，依赖图符合设计。
- 假采集器能生成真实时间戳的快照与历史投影。
- 某个采集器失败或变慢时其他通道继续更新。
- GUI 暂不消费视图时，采样历史仍正常记录，显示快照不积压。
- 通道满载、历史预算触发和退出行为有运行时验证。

## 阶段二 接入四类核心采集

先实现 CPU 与内存，再实现网卡计数和身份，最后实现物理磁盘 PDH、卷容量与设备发现。采集对象在自己的工作线程创建；Windows API 句柄使用 RAII 释放。

完成条件：

- CPU 总体和逻辑核心、内存、磁盘读写、卷容量、网卡收发都有来源明确的有效读数。
- 第一轮差分数据为采集中，累计计数回退和恢复不会生成尖峰。
- 同一 SSD 的多个分区不会重复加总物理磁盘 I/O；网络总览显示明确选择的接口。
- 本地卷和物理盘无法确认映射时，界面数据保持分开；网络卷默认排除。
- 热插拔、网卡断连和重命名会更新目录，旧数据有明确离线或过期状态。
- 普通用户权限运行核心功能；某项权限受限时报告该项原因。

## 阶段三 完成 GUI 和使用体验

先建立应用壳、主题、字体与通用组件，再完成总览、CPU、内存、磁盘、网络和设置页面。图表只消费引擎投影，设置通过命令应用和保存。

完成条件：

- 首屏四类卡片、详情页与历史范围切换可操作，所有数字来自采样结果。
- 配色、间距、文字层次和状态展示使用统一组件。
- 中文、长设备名称、最小窗口、最大化及 100%、150%、200% DPI 可读。
- 悬停读数、选中设备、键盘焦点和基础导航工作正常。
- 加载、不支持、失败、过期、设备消失状态均有可理解的界面反馈。
- 动效可关闭；最小化停止装饰动效，后台采样与历史连续。
- 设置重启后恢复，保存失败时明确区分已应用与未保存。

## 阶段四 稳定性与发行检查

用 Release 构建完成性能测量和长时间运行，按需要修复现有实现。整理便携包、字体许可和第三方许可，确认运行库依赖。

| 场景 | 检查方法 | 合格结果 |
| --- | --- | --- |
| 正常资源占用 | 参考设备预热后运行 5 分钟，记录整机归一化 CPU 与工作集 | 达到技术方案预算，超出时有实测原因与修正 |
| 8 小时运行 | 保持默认采样，检查工作集、线程数和错误量 | 无持续增长，无崩溃；历史与日志上限生效 |
| 睡眠恢复 | 睡眠后恢复，继续观察网络和磁盘 | 无恢复尖峰；有缺口和重新预热状态 |
| GUI 暂停消费 | 假 UI/测试客户端停止读取视图后恢复 | 正常采样仍入历史，恢复直接显示最近数据 |
| 慢采集 | 假采集器延迟超过多个周期 | 快速组仍更新，慢组变为过期，无无限重启线程 |
| 热插拔与断连 | 可移动盘、网卡断开与重连 | 无崩溃、身份不误合并、不支持数据不冒充 0 |
| 配置故障 | 无效字段、损坏 TOML、只读目录 | 默认或保留有效状态，原损坏文件不被自动覆盖 |
| 关闭 | 正常退出和模拟阻塞调用 | 正常线程 2 秒内结束；阻塞场景不无限等待 |
| 干净 Windows 环境 | 未安装 Rust 和开发工具的机器或虚拟机 | 便携包按说明直接运行，缺失组件有明确处理 |
| Windows 10 与远程桌面 | 在实际环境执行启动与主要交互 | 单独记录通过与局限，只有通过后才声明兼容 |

## 需要编写的运行时测试

以下测试针对不能只靠阅读代码确认的状态变化。普通 UI 组合、简单构造函数和直接字段转发不机械添加测试。

| 测试重点 | 具体断言 |
| --- | --- |
| 差分时间 | 1.2 秒内增加 1200 字节得到 1000 B/s，而不是按固定一秒计算 |
| 基线与回退 | 第一轮无速率；10000 回退到 100 后重新预热，不发生下溢或巨幅流量 |
| 源类型 | PDH 已格式化 B/s 直接入视图，不被第二次求差分 |
| 局部失败 | 网卡失败不会清空 CPU、内存；合法零流量仍保持 Ready |
| 过期 | 快速指标与 30 秒容量指标各自使用正确阈值，发布新快照不刷新旧成功时间 |
| 调度落后 | 跳过过期任务，不密集补跑；单个慢通道不会阻塞快速组 |
| 丢批 | 通道满载产生可观察缺口，恢复重建基线，内存不随批次数增长 |
| 历史限制 | 时间、1801 点和全局预算同时生效；离线设备最终清理 |
| UI 与采样隔离 | 不消费视图也能记录正常历史；最新槽恢复读取时没有陈旧队列 |
| 显示降采样 | 保持峰谷顺序与缺口，输出点数在上限内，不改变源历史 |
| 命令和关闭 | Busy 不应用设置，已接受命令有结果；满命令通道不阻止取消 |
| 配置保存 | 内存应用与持久化失败分开；临时写入失败不破坏最后有效文件；连续保存合并后每个请求仍有确认 |

算法与调度测试注入时钟；线程测试使用同步事件和可控假采集器。Windows 冒烟测试检查数值范围、计数状态和资源释放，不断言某个瞬时 CPU 百分比。

## 实施后的工程检查

Workspace 已建立。当前 fmt、Clippy、工作空间 Release 测试与构建已经执行；重复依赖未发现两套 egui/wgpu。可在 Windows 项目根目录重现：

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --release
cargo build --release
cargo run --release -- --smoke-test
cargo tree -d
```

需要权限、硬件或特定设备的 Windows 集成检查明确标记运行条件，不能因为自动环境跳过就宣称通过。每次修改运行对应必要检查，已通过后不无理由重复扩大测试范围。

## 开发优先级与首版完成定义

首要顺序为技术验证、模块边界、CPU/内存、网络、磁盘、完整 GUI、稳定性与发行。GPU 验证可在技术验证阶段完成，实际开发排在核心功能之后。

第一版完成要求四类监控数据有明确来源和状态，GUI 六个核心页面可用，历史有界、采集与渲染隔离、普通权限运行、异常场景可恢复，并通过约定测试与发行检查。达成后再扩展进程管理与告警，不把尚未实现的功能写成发布能力。
